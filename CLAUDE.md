## Commands

All commands run from `bot/`:

```bash
npm run lint          # ESLint
npm run typecheck     # tsc --noEmit
npm test              # Vitest (all tests)
npm run test:watch    # Vitest in watch mode (TDD)
npm run build         # tsc (compile to dist/)
npm start             # Run bot via tsx (no compile step)
npm run deploy-commands  # Register slash commands with Discord API
```

Run a single test file:
```bash
npx vitest run tests/services/jobService.test.ts
```

Before running the bot locally, start backing services (from the **repo root**, not `bot/`) and apply migrations:
```bash
docker compose up -d postgres redis   # Postgres on :5433, Redis on :6379
cd bot && npx prisma migrate deploy
```

Copy `bot/.env.example` to `bot/.env` and fill in `DISCORD_TOKEN`, `CLIENT_ID`, `DATABASE_URL`, and `REDIS_URL` before first run. For local docker compose use `DATABASE_URL=postgresql://chronobot:chronobot@localhost:5433/chronobot` and `REDIS_URL=redis://localhost:6379`.

After changing `prisma/schema.prisma`, regenerate the client:
```bash
npx prisma generate
```

## Architecture

The project is a single TypeScript ESM package under `bot/`. It runs via `tsx` (no compile step for dev/prod). CI runs lint → typecheck → test → docker build.

### Data flow

A Discord slash command → `commands/<name>.ts` → `JobService.createJob` → writes a `Job` row to Postgres and enqueues one BullMQ job per `sendTime` → `worker/processor.ts` fires at the scheduled time → `DiscordAdapter` sends the message → execution result written to the `executions` table.

### Key design decisions

**BullMQ job IDs**: BullMQ forbids `:` in custom job IDs (used as Redis key delimiters). The ID format is `<uuid>_<isoTime-with-colons-replaced-by-underscores>`, generated by `bullmqJobId()` in `JobService`.

**`sendTimes` array**: A single Prisma `Job` holds an array of ISO timestamp strings. Each entry becomes its own BullMQ job. After a send-time fires successfully, that entry is removed from the array; when empty, the `Job` row is hard-deleted.

**Idempotency**: The `executions` table has a unique index on `bullmqJobId`. Before processing, the worker checks for an existing `COMPLETED` execution for that ID and skips if found — protecting against duplicate BullMQ deliveries.

**Startup restore**: `JobService.restoreJobs` re-enqueues all `QUEUED` jobs on bot startup (handles restarts and downtime). It also prunes send times that are now in the past and hard-deletes any terminal-state (`COMPLETED`/`FAILED`/`DEAD`) job records left over from before hard-delete was adopted.

**Rollback on enqueue failure**: If BullMQ throws during `createJob`, the just-created Postgres row is hard-deleted so users don't see ghost jobs.

### Module layout

- `src/commands/` — one file per slash command, **auto-loaded** by `index.ts` at startup. Each exports a default with `data` (SlashCommandBuilder) and `execute`. Adding a new `.ts` file here is all that's needed to register a new command (then run `deploy-commands`).
- `src/events/` — Discord.js event handlers, also auto-loaded. Each exports `name`, optional `once`, and `execute`.
- `src/services/JobService.ts` — coordinates Prisma + BullMQ; owns enqueue logic and `restoreJobs`.
- `src/worker/processor.ts` — BullMQ `Worker` with concurrency 5; handles retry/dead-letter and execution audit trail.
- `src/repositories/` — thin Prisma wrappers (`JobRepository`, `ExecutionRepository`).
- `src/queue/queues.ts` — exports the `jobQueue` BullMQ Queue instance. `jobTypes.ts` defines the typed `QueuedJobData` payload `{ jobId, channelId, isoTime }`.
- `src/adapters/` — `Adapter` interface + `DiscordAdapter` implementation; swappable for testing.
- `src/metrics/` — `prom-client` counters/histograms/gauges + HTTP server exposing `/metrics` and `/healthz` on `METRICS_PORT` (default 9090).
- `src/config.ts` — Zod-validated env schema; crashes at startup with a clear message if required vars are missing.
- `prisma/schema.prisma` — two models: `Job` (status: QUEUED/COMPLETED/FAILED/DEAD) and `Execution` (status: STARTED/COMPLETED/FAILED).

### Business rules

- **Per-user limit**: max 5 `QUEUED` jobs per Discord user (`countByUserId` check in `/schedule`).
- **Frequency expansion**: `once` → 1 send time; `daily` → 7 consecutive days; `weekly` → 4 consecutive weeks.
- **Timestamp input**: `YYYY-MM-DD HH:mm` UTC; must be at least 10 seconds in the future.
- **All replies are ephemeral**: `interactionCreate` defers every interaction with `flags: 64` before calling `execute`.

### Tests

Tests live in `bot/tests/` (mirroring `src/`) and run with Vitest. They mock Prisma and BullMQ — no live database or Redis required.
